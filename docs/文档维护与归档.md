已实现、软件通过、裸板通过、最终硬件通过、游戏通过分别写。不同日期/板型的结果不得合并成“全部完成”。`build/`可覆盖生成报告不能代替冻结证据，hello宣称的能力不是验收报告。

## 后续更新规则

1. 改某模块：更新`docs/modules/`对应文档的行为、源码入口、验证和未完成项。
2. 改公共接口/协议/schema/版本格式：同步公共契约、受影响模块、CDC命令表与测试入口；写清兼容/迁移。每次正式编译交付UF2/ELF文件名带实际固件版本号，保存到独立构建时间目录及摘要清单，按[运行发布](../RUN_INTEGRATED.md)执行。
3. 新实测：原始证据新增日期/版本目录，更新[测试状态表](测试状态与待验收.md)，不能覆盖旧失败记录或改其SHA。
4. 完成产品决策：更新[产品约束](产品需求与约束.md)，技术默认仍注明工程策略。
5. 文档链接或结构改变：运行`python docs/tools/verify_docs.py`。`--audit-snapshot`额外核对2026-10-05整理前代码/证据基线，用于此次归档审计；后续正常开发不用该参数限制新的代码改动。归档稿尽量冻结；只修导航，事实更新写在现行文档。

文档检查报告见[DOCUMENTATION_CHECK.json](archive/2026-10-05/DOCUMENTATION_CHECK.json)，归档路径/原始与重定位后SHA见[ARCHIVE_MANIFEST.json](archive/2026-10-05/ARCHIVE_MANIFEST.json)。检查覆盖现行入口、兼容导航、模块及归档链接；源码和冻结证据完整性另核对整理前保护清单。历史第三方/旧板说明中的已删除构建产物链接按[归档说明](archive/2026-10-05/README.md)解读。
